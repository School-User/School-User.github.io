Spotify AI DJ Patch

My open-source Spotify client could do everything except the one feature I actually wanted: the AI DJ. So I reverse-engineered Spotify's DJ session and voice-narration protocol and patched it in — then sent the work upstream.

RustlibrespotProtocol REOpen Source

The missing feature

I use an open-source Rust Spotify client built on librespot instead of the official app. It's fast and lightweight, but Spotify's AI DJ — the feature that auto-queues music with spoken commentary between tracks — simply didn't work: selecting it resolved to an empty, silent playlist. Official clients support it; librespot-based ones didn't.

Reverse-engineering DJ sessions

DJ turned out to be its own small protocol layered on top of normal playback, keyed off an allowlisted internal URI scheme. Getting it working meant handling several pieces that don't exist anywhere in normal track playback:

  • Following a session-context URL to actually resolve what the DJ wants to play next, since it isn't a normal static playlist
  • Lazily paging in the next batch of tracks only as needed, rather than fetching an entire session up front
  • Fetching the DJ's spoken narration itself — a separate API call returning a redirect to an MP3 on Spotify's CDN — and decoding/mixing it (mono) alongside the actual music track
  • Wrapping the normal track-decode pipeline so intro and outro narration play at the right moment relative to the song, not just before or after it

One subtle protocol bug surfaced during testing: the pagination response for "what's next in this DJ session" comes back as a different JSON shape than a normal playback context, and treating it like one silently broke paging past the first batch of tracks.

Respecting rate limits the hard way

Spotify's DJ session state is tied to the account and accumulates every segment anyone requests against it — including my own repeated test runs — so aggressive automated testing actually degraded the real experience by inflating and repeating the session. Skipping too fast during testing (tens of skips per minute) also got audio key requests throttled for upwards of 20 minutes at a time. Both meant testing had to happen at a realistic, human pace rather than scripted as fast as possible — an unusual constraint for software testing, where "run it in a tight loop" is normally exactly right.

Sending it upstream

Once working, I opened a pull request against librespot itself (the underlying library my client depends on, maintained separately from the client), rather than keeping the patch local — DJ support benefits every client built on librespot, not just mine. The maintainer of my specific client had already declined to build DJ support independently, citing it as out of scope unless proper upstream support existed first — which made landing it in librespot the only path to a real, lasting fix rather than a fork only I could use.

The PR went through real review: the librespot maintainer came back with eight specific points across API shape and edge-case handling, all addressed in a follow-up commit, with CI green throughout. That back-and-forth is the part of open source that's easy to skip in a personal fork — it's also what makes the fix something other people can actually depend on.
