Cybersecurity LLM Fine-Tune

Fine-tuned Qwen2.5-7B on cybersecurity data with QLoRA, served it locally — then used it as the base for a mechanistic-interpretability experiment in identifying and editing exactly how a model refuses.

QLoRAUnslothQwen2.5-7BOllamaPyTorch

The fine-tune

Base model: unsloth/Qwen2.5-7B-Instruct-bnb-4bit, trained with a QLoRA adapter (rank 16, applied across all attention and MLP projection matrices) on the Trendyol Cybersecurity Instruction-Tuning Dataset, using Unsloth and TRL's SFTTrainer. One epoch took about 12 hours on a single RTX 3070 Ti. The adapter — not the merged weights — is the source of truth I kept, since everything else downstream is reproducible from it.

Once trained, it got registered in Ollama and wired in as one of the proposer models in my local Mixture-of-Agents pipeline, so it's actually in the rotation answering real queries, not just a benchmark artifact.

Going deeper: how does refusal actually work?

After the fine-tune shipped, I wanted to understand the mechanism behind why a model refuses certain requests — not just that it does. That turned into a small interpretability experiment: finding the internal "refusal direction" in the model's residual stream and testing whether editing it out changes behavior predictably.

First attempt was a lesson in why you verify before you commit. I picked a layer arbitrarily, ablated it across the model's projection matrices, and the model refused identically — no effect at all. The weight edit is permanent and expensive to redo, so shooting from the hip on layer choice was the wrong approach.

Doing it properly: validate before you edit

The fix was separating finding a candidate direction from committing to one. I wrote a scan that:

  • computes a mean-difference "refusal direction" per candidate layer, from a small set of contrastive prompt pairs (harmful vs. harmless)
  • before touching any weights, live-tests each candidate direction with temporary forward hooks across the entire residual stream — every layer's output, not just isolated sub-modules, since hooking submodules alone doesn't reproduce the real effect
  • scores each candidate against held-out prompts the direction wasn't computed from, so the result isn't just overfit to the calibration set

The arbitrary first guess (layer 18 of 29) scored effectively 0/2 in live testing. The actual best candidate, layer 14, scored 6/6. Only after that empirical check did I save the winning direction and apply it permanently — projecting it out of every matrix that writes into the residual stream.

This variant is a local research artifact only, kept off anything user-facing. The point of the experiment was understanding and controlling a specific interpretability mechanism, not shipping an unsafe model — it stays isolated from the fine-tune that's actually in production use.

Fighting a 14GB RAM budget

The whole pipeline had to run on a box with 14GB of RAM (plus swap), which doesn't comfortably fit a full fp16 7B model in memory at once. Two workarounds made it possible: computing the hidden states used for the refusal direction on the 4-bit adapter model (cheap, GPU-resident, no RAM pressure), and editing the final merged fp16 weights shard-by-shard — loading and saving one safetensors shard at a time instead of ever materializing the full model as a live module. Disk was the other constraint: each full merge-to-fp16 pass, GGUF conversion, and quantization step leaves large, fully-reproducible intermediates behind, so cleaning those up after each successful registration kept the box from filling up.
