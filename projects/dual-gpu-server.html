Dual-GPU AI Server

Pooling an NVIDIA RTX 3070 Ti and an AMD RX 6700 XT — two GPUs from rival vendors — through Vulkan, so one large language model runs split across both at once.

OllamaVulkanllama.cppLinuxsystemd

The problem

My AI box started with one GPU, an RTX 3070 Ti with 8GB of VRAM — enough for small-to-mid local models, but anything in the 20B+ range either wouldn't fit or spilled most of itself into system RAM, which tanks speed. I added a second card, an AMD RX 6700 XT with 12GB, to get more VRAM headroom.

The catch: Ollama can see both cards fine on their own — NVIDIA through CUDA, AMD through Vulkan — but by default a single model load only uses one backend at a time. Setting the obvious-looking OLLAMA_SCHED_SPREAD=1 flag doesn't fix this on its own; it only spreads a model across multiple GPUs that are already on the same backend. A 30B model still spilled most of its weight to slow CPU RAM instead of using the free VRAM sitting on the other card.

The fix

The trick was forcing both GPUs onto the same backend so llama.cpp's Vulkan multi-device support could split one model's layers across both of them. A systemd override on the Ollama service does it:

Environment=OLLAMA_SCHED_SPREAD=1
Environment=CUDA_VISIBLE_DEVICES=

Setting CUDA_VISIBLE_DEVICES to empty hides the RTX 3070 Ti from the CUDA backend entirely, so it only shows up via Vulkan — same backend as the AMD card, same pool. That gets a combined ~20GB of VRAM that llama.cpp can split a single model across, instead of two separate 8GB/12GB pools.

The tradeoff: every model now runs through Vulkan instead of the 3070 Ti's native CUDA path, which costs a modest amount of per-token speed on small models that would've fit on one card anyway. I took that tradeoff on purpose — getting 30B+ models mostly on-GPU mattered more to me than peak speed on models that were already fast.

Results

Before: a 19GB 30B model ran 61% GPU / 39% CPU on the AMD card alone. After the Vulkan pool, the same model loads ~97% GPU / 3% CPU, split roughly 18 layers on the 3070 Ti and 31 layers on the 6700 XT.

Current benchmarks across both cards (300-token generations):

  • gemma4:26b-a4b-it-qat — 34 tok/s, 96% GPU
  • qwen3-30b-abliterated — 51 tok/s, 98% GPU
  • qwen3-coder-abliterated (iq3, 32k ctx) — 45 tok/s, 100% GPU

What I'd watch for

The one gotcha that cost real debugging time: an occasional bad split traced back to low system RAM, not the Vulkan config itself. When free RAM gets tight, Ollama's scheduler gets conservative and can degrade to a worse CPU-staged split that looks identical to a broken GPU config. The fix wasn't touching the Vulkan setup at all — it was freeing up system RAM (in my case, removing an idle service that was quietly eating 15GB). Lesson: before debugging a GPU-split problem, check free system RAM first.
