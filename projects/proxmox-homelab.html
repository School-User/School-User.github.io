Proxmox Homelab

A decommissioned enterprise server running my file storage, a Minecraft server, AI training/serving sandboxes, and test VMs — all reachable privately over Tailscale instead of exposed to the internet.

Proxmox VELXCTailscaleNetworkingDebian

The hardware

The host is a Dell PowerEdge R640, dual Xeon Silver (40 threads total) with well over 100GB of RAM — enterprise rack hardware with no GPU, running Proxmox VE. Most of that capacity sits idle most of the time, which makes it a good fit for a pile of small, isolated workloads rather than one big one.

What's running on it

  • NAS — a Samba file-share container with its own Tailscale identity, reachable from anywhere on my tailnet, not just at home
  • Minecraft — a Paper server, deliberately kept off the public internet and off router port-forwarding. It's exposed only through a Tailscale-proxied TCP connection, so only people on my tailnet can even find it
  • nanoGPT training sandbox — a CPU-only container for small from-scratch model experiments, explicitly capped on cores/RAM/scheduling priority so it can never starve the other services sharing the box
  • Self-hosted AI agent — the always-on Telegram/email agent described in its own write-up
  • Assorted test VMs for one-off projects

Locking down a game server people actually use

Minecraft in offline mode means anyone can claim any username — there's no real account verification behind it. Running it Tailscale-only closes off random internet scanners, but friends on the tailnet could still impersonate each other by username alone. I added an authentication plugin (picked an open-source one over a more popular closed-source alternative, specifically so the auth logic is auditable) requiring a password on first join.

Caught a real foot-gun in that plugin's default config before it shipped: because every player connects through the same Tailscale proxy, they all appear to the server as the same local IP address. The plugin's default "skip login if same IP as last session" convenience feature would have let anyone log in as anyone, since every player shares that IP. Disabling IP-based session skipping was a one-line config fix, but the kind that's invisible until someone actually exploits it.

Taking down my own network

The messiest incident: I wired two of the server's spare network ports into the home network to let it also act as a switch for other devices — without first confirming spanning tree was correctly configured on the new bridge. Both ports being live without loop protection created a bridge loop, and the whole home LAN went down for about 90 minutes. The kernel logs were unambiguous once I looked — thousands of "received packet with own address as source" warnings, the signature of a switching loop. Turning spanning tree protocol back on for that bridge fixed it immediately and permanently. Lesson learned the expensive way: never add a bridge port to a live network without verifying loop protection is actually active, not just configured.

One address for everything

With several services spread across different VMs and containers, remembering (and re-sharing) a different IP for each one got old fast. I set up a single friendly hostname on the server host that reverse-proxies/forwards specific ports to the right guest automatically — so every service is reachable from one memorable address, and I only need to update one place if a guest's internal address ever changes.
