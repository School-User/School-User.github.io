Byte to Bite: BEST Robotics Simulator

A 3D browser game that recreates the 2026 BEST Robotics "Byte to Bite" field, so my team can practice driving and strategy before the real robot even exists — playable with a keyboard, or with an actual VEX controller.

Three.jsJavaScriptVEX EXPWebSocketSupabase

Why build this

Our BEST Robotics team's actual robot doesn't exist yet when the season's field design drops — but strategy and driving practice can't wait for hardware. So I built a browser-playable 3D recreation of the official 2026 "Byte to Bite" field: Three.js, no build step, plain ES modules loaded straight from a CDN. Pick up plates and cups and deliver them before the 3-minute match clock runs out, same rules as the real competition. Each player gets 8 plates and 8 cups on their own side of the field.

To get the field geometry right, I worked from VEX's own field CAD files and official drawings rather than guessing dimensions by eye — the walls, dividers, and scoring zones in the game match the real field's published measurements.

The wall you could drive through

Early on, the robot could drive straight through one of the interior divider walls — a collision bug that was unusually hard to pin down. The collision boxes themselves checked out: decoded directly from the field model's geometry data, with correct, sensible coordinates, and a passing automated test suite. But something was still letting the robot tunnel through in actual play.

Debugging a physics bug that only shows up to a human playing the game, not to an automated test, meant building better tools to see it happening: a live on-screen HUD showing the robot's exact position and collision state every frame, plus a headless Chromium harness running 120,000 randomized moves against the collision boxes to brute-force a reproduction. That harness never reproduced the divider bug — the 5 wall boxes were solid and correctly aligned.

The real bug turned out to be somewhere else entirely: the field model only had closing walls on two of its four outer edges. The robot wasn't tunneling through the divider — it was driving around it, off the field's open edges, and reappearing on the other side. Two mirrored boundary boxes fixed it. A classic case of the reported symptom and the actual defect living in different places.

Driving it with a real controller

Keyboard controls work, but I wanted the practice to feel like the real thing — so the game also supports a genuine VEX EXP controller as input. That meant reverse-engineering how the controller actually talks over USB (see the separate write-up on that), then building a small bridge: a C++ program on the VEX Brain streams live joystick/button state over serial, a Python bridge reads it and rebroadcasts over a local WebSocket, and the game connects to that socket and maps the controller state directly onto the same input handling the keyboard uses. Zero duplicated movement logic between the two input methods.

Going multiplayer

Single-player practice is useful, but real matches are several robots at once, so I built a multiplayer mode on top of the same codebase: up to four players per room, one robot per field quadrant, a 15-second lobby before each match (no joining mid-match), a server-run match clock so everyone sees the same timer, and synced robot state over WebSocket. A fifth player automatically lands in a new room. Restart is intentionally off in multiplayer, so a stray keypress can't reset a live match for everyone.

The hosting split was a deliberate call: the static game and its menu stay on GitHub Pages, which is free and requires nothing from players beyond opening a URL. The multiplayer server is a small Node process on Google Cloud Run in us-central1, reached over wss:// from the page. It started on a Google Cloud VM, and I moved it to Cloud Run because the school's web filter blocked the VM's address (and several other free hosts) while letting run.app through. The tradeoff is that Cloud Run scales to zero when idle, so the first player after a quiet spell may wait a few seconds. I chose cloud hosting over routing multiplayer traffic through my own home server, specifically to avoid putting public internet load on my home network. Load-tested on the earlier VM host with 20 simulated players across five rooms, with the server using about 65 MB of RAM during the test.

Players never install anything or pick a server; they open the GitHub Pages link, and the menu's Multiplayer option handles connecting to the server behind the scenes.

Making it run on school laptops

The game gets played on slow school laptops, so I added a Settings menu (gear button or Esc): graphics quality Auto/Low/Medium/High, a 30/60/Max frame rate cap, a minimap toggle, and an FPS counter. Auto steps the quality down if frames drop. The game also stops drawing behind the start menu, drops to 15 fps when the tab is unfocused, and refreshes shadows every other frame. On the other end, an optional RTX mode adds ambient occlusion, bloom, bigger shadow maps and full-resolution rendering for a ray-traced look. It is post-processing, not real ray tracing, and it is off by default because it needs a strong GPU. My first version made the whole scene glow white: the bloom threshold was set against pre-tone-mapping light values, where a sunlit white floor is already brighter than 1, so I raised it.

Testing it on my own laptop showed another wrinkle: the browser was rendering on the integrated AMD GPU and leaving the RTX 5050 idle. Forcing Chrome onto the NVIDIA card crashed its GPU process on native Wayland, because the frames can't be handed to the AMD chip that draws the screen. Running Chrome through XWayland fixed it, and the game now runs on the dedicated GPU.

Knowing who's actually playing

I added a lightweight, privacy-respecting usage counter backed by Supabase: an allow/reject banner on first visit, with counts (not identities) logged either way, and play sessions logged separately when someone actually starts a match. A public read-only view exposes aggregate stats — total visitors, plays, unique players, multiplayer plays — without exposing row-level data, so I can see whether the game is actually getting used without tracking anyone individually. As of November 7, 2026 it shows 33 visitors, 23 players and 78 matches started (46 of them multiplayer), counted since October 13.
