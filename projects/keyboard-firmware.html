Keyboard Firmware Dump

My mechanical keyboard runs a chip too old for QMK and too obscure for any existing flashing tool. Getting at its firmware meant going around both problems.

SinoWealth SH68F90sinowispRustWindows VM passthrough

The chip nobody supports

My keyboard runs a SinoWealth SH68F90 — an 8051-family microcontroller. QMK, the open-source firmware most hobbyists reach for, simply can't run on 8051 hardware. The usual community flashing tools (SMK, sinowealth-kb-tool) don't list this chip either. So before any custom firmware work could start, I needed two separate things: a way to update the stock firmware, and a way to read it back out.

Updating official firmware, the hard way

The vendor's official updater is Windows-only, and the keyboard's bootloader re-enumerates as a different USB device ID when it drops into ISP (in-system programming) mode. To make that work from Linux, I passed the keyboard through to a Windows VM at the USB port level (not a static device ID), so the bootloader's re-enumeration follows the device into the VM instead of breaking the passthrough. A temporary udev rule opened permissions on the new device node for the handoff, then got removed again afterward.

Smaller annoyance along the way: typing into the VM over QMP was silently dropping every p character, and PowerShell refused to run at all ("cannot access the specified device"). Worked around it by using cmd with a one-line curl to a locally served batch file — a command that happens to contain no p.

Reading the firmware back out

For actually dumping and inspecting the firmware, I used sinowisp, a Rust tool that happens to support this exact chip family. It reboots the keyboard into ISP mode and back automatically:

sinowisp read -p sh68f90 --vendor_id 0x12c9 --product_id 0x6001 --format bin out.bin

That gave a clean 61,440-byte dump with the bootloader itself untouched, which I kept as a verified backup — important, since this is the only known-good copy of the stock firmware for this board.

Mapping the keymap

With a firmware dump in hand, I located the keymap table by inspecting the binary directly: plain HID usage codes, laid out column-major across 6 rows per column, with the base layer starting around offset 0x67fa and an Fn layer around 0x6878. That table is the actual target for future remaps — modifier key handling isn't in it yet, which is the next thing to work out.

This backup already paid off once: the keyboard started "acting weird" later on, and I was able to restore it to exactly-stock in about 30 seconds with sinowisp write — no Windows VM needed for a restore, only for the official updater. Diffing the two dumps showed the drift was 4 bytes in a settings block, not the firmware code itself.
