VEX Controller → Linux Gamepad

I wanted to drive my Byte to Bite browser sim with a real VEX controller. That turned into weeks of USB protocol archaeology before it finally worked — as a real, system-wide Linux joystick.

It's not a gamepad — it's two serial ports

First surprise: the VEX EXP Controller doesn't enumerate as a USB HID gamepad at all. It shows up as two CDC-ACM serial ports. That means the browser's Gamepad API can never see it directly, with or without touching the game's code — whatever I built would need a bridge translating serial data into something the browser or OS actually understands as a controller.

Reverse-engineering VEX's framing

Using VEX's open-source vex-v5-serial Rust crate as a reference, I got the "CDC2" packet framing working — header bytes, command byte, a variable-length size field, payload, and a CRC16-XMODEM checksum. One of the two serial ports actually answered to correctly-framed requests; the other stayed silent.

Then came a run of dead ends. The obvious "get controller state" command replied, but the payload jittered randomly with zero correlation to real stick or button input in a synchronized test where I held each input on command — it was a status/heartbeat field, not telemetry. A calibration-start command visibly changed the baseline pattern, proving the command did something, but still no usable joystick data. Several other diagnostic commands replied with nothing resembling live input at all.

The working theory that explained all of it: an unbound controller (no paired Brain) genuinely has no live joystick telemetry to give over USB. Its normal job is relaying raw RF frames to a Brain, not exposing local analog state to a PC on its own.

Getting a Brain didn't immediately fix it

A VEX EXP Brain became available, which should have unlocked the documented protocol path. Instead it hit a different wall: the hardware was too new for the existing open-source tooling. PROS-CLI didn't recognize the EXP Brain's product code at all — I patched its device tables and a status-schema length bug to get past that, which got device status and file-transfer initiation working (a real, documented ACK byte came back — solid proof the protocol/CRC work was correct). But program upload still failed: the EXP Brain's flash addressing doesn't match what that CLI assumes, and that's a different memory map, not a small patch.

cargo-v5 / vex-v5-serial, the actively maintained Rust alternative, hit its own version-drift wall — the published crate didn't recognize a device-type byte this EXP firmware reports, and the unpublished git fix for that was built against a newer API that the CLI tool hadn't caught up to yet. Two independent open-source tools, two different gaps.

Turned out neither gap was mine to close: VEX's own developers have confirmed PROS was never given an EXP SDK — "V5 is the only product where partner developers were involved." Not a bug to patch around, a hard vendor limitation.

The actual fix: VEX's own tooling

The path that worked was VEX's official VS Code extension plus its vexcom CLI, running a small uploaded C++ program that prints live controller state over serial. A Python bridge reads that serial stream and does three things at once from a single read: feeds the browser game over WebSocket, and creates a genuine virtual joystick device via Linux's evdev.UInput — axes, face buttons, D-pad, all of it.

End result: the controller now works as a real joystick for any Linux app that reads standard gamepads — not just my own game.
